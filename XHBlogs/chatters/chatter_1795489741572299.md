## 今日概览

今天两条主线，一条在概念层，一条在工程层。

* **概念层**：把「分层」这个词拆开——HNSW 的分层是几何尺度上的分层，GraphRAG 的 Leiden 分层是语义抽象上的分层；再把 LLM / Harness / Agent 三个词还原成同一个东西的三层壳。
* **工程层**：从一次 Electron 应用启动崩溃，走完「堆栈定位 → 源码确认约束 → 官方清单校验 → 最小侵入恢复 → 实测验证」的完整闭环；另外还有云厂商免费层的额度口径与注册风控排查顺序。

两条线其实回答的是同一个问题：**context 是稀缺资源，谁负责决定什么进来、什么出去。**

## 一、HNSW、IVF、KNN、ANN：先把四个词摆回各自的层

### 结论

当时那句话里揉了三层不同的东西，所以名字捞不出来。正确的分层是：

| 词 | 它实际是什么 | 所在层 |
| --- | --- | --- |
| KNN | 任务定义：精确找出 k 个最近邻 | 目标 |
| ANN | 工程妥协：允许少量漏召回，换速度 | 目标（近似版） |
| HNSW | 索引数据结构：分层图 + 贪心下降 | 实现 |
| IVF | 另一种索引：k-means 分桶后再精搜 | 实现 |

一处关键纠正：**KNN 和 ANN 不是两种算法。** KNN 要的是数学上确定的那 k 个，代价是必须算完 N 个距离，$O(N \cdot d)$；ANN 是「可以接受 95% 命中，换 100 倍速度」。HNSW 是 ANN 的一个实现，不是 KNN 的。别把这三个当同义词背。

### HNSW 要杀掉的到底是什么

N 个 d 维向量，来一个 query，精确算就得跟全部 N 个比一遍，N 到千万级就废了。

第一版想法很自然：**建一张近邻图**。每个点连几个邻居，查询从随机入口开始，每次跳到「离 query 更近的邻居」，走到没有更近的邻居为止——这就是 NSW（可导航小世界）。它的硬伤是**单层**：早期插进来的点度数越来越高，慢慢变成枢纽；贪心走几步就容易卡在局部最优；平均跳数随 N 增长。

HNSW 砍的那一刀是从**跳表（skip list）借来的：给每个节点按指数分布随机分配一个最大层 ℓ。越高的层节点越稀少、边越长（跨越大片空间）；第 0 层包含所有**节点、边最短最密。

于是查询变成逐层导航：

```
顶层（极稀疏，长边）
  ↓ 从入口点贪心跳，几步跨到 query 所在的大致区域
中间层（边变短，区域收窄）
  ↓ 同一个点作为下一层入口，继续贪心
第 0 层（全量节点，短边）
  ↓ 用 efSearch 大小的候选池做 beam search，取 top-k
```

**关键直觉**：上层是高速公路，只花几次距离计算就把你从任意位置扔到目标附近；下层才做精细比较。距离计算次数从 $O(N)$ 压到约 $O(\log N)$。代价就是「近似」——贪心下降可能停在局部最优，真邻居未必被访问到。

### 三个旋钮

| 参数 | 管什么 | 什么时候调 |
| --- | --- | --- |
| `M` | 每个节点最大连接数 | 建库定死。大 → 图更连通、内存涨 |
| `efConstruction` | 建图时候选池大小 | 建库定死。大 → 图质量高、建得慢 |
| `efSearch` | 查询时候选池大小 | **运行时可动态调**。大 → recall 高、延迟高 |

`efSearch` 能在查询时单独调这点很实用：同一个索引，简单查询调小、重要查询调大，不用重建。层分布参数 $m\_L$ 论文建议取 $1/\ln(M)$，对应跳表里「平均单层重叠一个元素」的平衡点，一般不用动。

### 「先圈范围再精搜」其实是 IVF

原话里那句「选确定大致范围、缩短检索时间」更像 **IVF**（Inverted File Index）：

```
建库：k-means 把向量空间切成 nlist 个桶（Voronoi 单元），每桶一个质心
查询：query 先跟全部质心比一遍 → 挑最近的 nprobe 个桶
     → 只在这几个桶里做精确距离计算 → 取 top-k
```

同样叫「圈范围」，机制完全不同：IVF 靠**全局聚类**划地盘，HNSW 靠**图上的长边**跨空间。

| ‍ | HNSW | IVF |
| --- | --- | --- |
| 圈范围的方式 | 分层图贪心下降 | k-means 质心分桶 |
| 高维 / 分布不均 | 较稳，不依赖全局聚类 | 质心漂移会伤 recall，需定期重建 |
| 内存 | 高（要存图边，约 2 倍） | 低 |
| 增量插入 | 天然支持 | 改 `nlist` 得重建 |
| 调参 | `efSearch` 运行时可调 | `nprobe` 运行时可调，`nlist` 建库定死 |
| 压缩配合 | 可配 PQ，但别扭 | IVF+PQ 是标配 |

超大规模常见组合是 `IVF10000_HNSW32,PQ16`——HNSW 反过来给 IVF 当 coarse quantizer，专门加速「从一万个质心里找最近几个」这一步。所以这两个不是二选一，是能叠的。

### 一个方向性错误

原话里「从精确的每一个匹配，选确定大致范围」把方向记反了。第 0 层确实包含全部节点（最「精确」的一层），但**查询是从最稀疏的顶层往下走**，不是从底层往上筛。

这个方向一错，就容易把它理解成「层层过滤」，而它其实是「层层导航」。差别在于：过滤会丢弃候选，导航只是换入口点，候选池一路带着往下走。

## 二、两个「分层」不是一回事

### 结论

之所以把 GraphRAG 的 Leiden 社区层级和 HNSW 的分层联想到一起，是因为**都长得像金字塔**。但它们分的东西根本不同：

| ‍ | GraphRAG 的 Leiden 社区层级 | HNSW 的分层 |
| --- | --- | --- |
| 分的是什么 | **知识的抽象层级** | **距离的尺度层级** |
| 节点是什么 | 实体 → 社区 → 上层主题 | 每一层都是同一批向量点的副本 |
| 层间关系 | 由连接密度聚类归纳出来 | 由指数分布随机分配，插入时定 |
| 层里存什么 | LLM 写好的社区报告（语义摘要） | 图边（邻接关系），无语义 |
| 查询时怎么用 | 挑 Local / Global / DRIFT 模式去读报告 | 必须从顶层入口逐层下降到 0 层 |
| 解决什么 | 答案不在任何单个 chunk 里 | 精确算 N 个距离太慢 |
| 属于哪一层 | 检索 / 推理策略 | 存储 / 索引实现 |

一句话：**Leiden 分的是「这些概念在讲什么」，HNSW 分的是「这些点离多远」。** 一个在语义空间，一个在几何空间，只是都画成了金字塔。

### 它们在真实系统里是上下游，不是替代关系

LightRAG 把图节点嵌成向量丢进向量库，查询时先用低层 / 高层关键词做向量检索——**那一步底层跑的就是 HNSW**——拿到候选实体后，再走一跳邻居拿关系。所以是 HNSW 替图检索干活。

顺着这个往下接：Hybrid 检索里「稠密」那一路，底下就是 HNSW 或 IVF 在扛；BM25 是倒排索引，跟它们完全两套机制。这才是「混合」这个词的分量——两路连失败模式都不一样，所以互补。

## 三、LLM、Harness、Agent：三层壳

### 结论

这三个词不是并列的概念，是同一个东西的三层壳。

> **LLM 是一个无状态的纯函数；Harness 是包在它外面、让它能干活的全部软件；Agent 是这两者合起来之后、正在执行任务的那个整体。**

行业 shorthand：**Agent = Model + Harness**。

### 最里层：LLM 到底做什么

剥掉神秘感，机制上它只有一行：

```
f( token 序列 )  →  下一个 token 的概率分布  →  采样  →  一个 token
```

它原生不具备四样能力：

| 它不会 | 为什么 |
| --- | --- |
| 记住上一句话 | 每次调用都是全新的前向传播，权重不变、无内部状态 |
| 执行代码 / 读文件 | 它只输出 token，没有副作用 |
| 知道实时信息 | 权重训练完就冻结了 |
| 判断自己做得对不对 | 它看不到动作的结果，除非有人把结果喂回来 |

这里有个必须先绕过去的坑：**「ChatGPT 能记住上下文」不是模型的能力，是壳的能力。** 每发一句，外面的程序把整段历史重新拼成一个 token 序列再送进去。模型从头到尾只见过「一长串文本」，它以为这是第一次见到你。

所以光是「聊天」这个界面，就已经是一个 harness 了——那个装消息的 list 加那个 while 循环，是有史以来最小的 harness。

关于「LLM 如何理解」：机制上它没有「理解」这个独立动作。能力来自训练时压进权重的模式，而**某一刻被激活哪部分能力，完全由 context 决定**。所谓「懂了」，是你给的那串 token 恰好把对应模式激活了。这句话能解释后面几乎所有怪现象。

### 中间层：harness 是怎么长出来的

从最小 harness 往外长，每加一样东西，都是因为模型缺一样东西：

```
最小 harness:  消息列表 + while 循环
     ↓ 模型只能说，不能做
+ 工具注册表     （模型说「我要 grep」，壳去查工具、验权限、执行、把结果塞回 context）
     ↓ 多轮之后 context 撑不住
+ 上下文管理     （compaction 压缩、大工具结果卸载到文件系统、按需加载 skill）
     ↓ 模型会谎报「我做完了」
+ 反馈与校验     （跑测试 / linter / 类型检查，把失败结果送回去）
     ↓ 会跑飞、会死循环
+ 权限与护栏     （审批门、turn 上限、时间与预算上限、循环检测）
     ↓ 单次会话装不下长任务
+ 状态持久化     （session DB、进度文件、todo、断点恢复）
     ↓ 一个 context 装不下所有子任务
+ 子 agent       （隔离子会话、受限工具集）
     ↓ 怎么知道改好了没
+ 评估层         （tracing、eval、回归门禁）
```

核心就一条：**开环变闭环。**

模型裸着是 `Reason → 输出 → 结束`，一次性文本生成器，看不见后果。套上 harness 是 `Reason → Act → Observe → Verify → Repeat`，能读文件、改代码、跑测试、看见红灯、再改。这就是 ReAct 那个循环，也是 harness 全部价值的来源。

由此得出那个反直觉但极重要的结论：**同一个模型，换一套 harness，表现能差一大截。** 因为能力不全在权重里，有一半在那个 while 循环怎么写。

### 三个最容易混的词

| 词 | 是什么 | 例子 |
| --- | --- | --- |
| Agent framework | 给你零件，你自己组装 | LangGraph、CrewAI、AutoGen |
| Agent harness | 开箱即用的成品，架构已经定死 | Claude Code、Codex CLI、Cursor、Hermes |
| Agent SDK | 原材料，只有 function calling 原语，没有运行时循环 | 各家 SDK |

判据很简单：**运行时有没有真的在跑那个「根据上一步观察决定下一步」的内循环。** 框架把这个决定权留给人类架构师，harness 自己就跑起来了。

还有一个必须拆的同名冲突：

* **Agent harness**：任务**进行中**驱动循环，根据观察决定下一步
* **Eval harness**：任务**结束后**打分（SWE-bench 那类），它的循环是「遍历任务收集分数」，不参与决策

一句话分：**一个在事后记录，一个在事中决策。** eval harness 是 agent harness 的 assurance 层的一部分，不是替代品。

### 三层工程的范围

| 学科 | 改什么 | 作用域 |
| --- | --- | --- |
| Prompt engineering | 措辞 | 单次模型调用 |
| Context engineering | 每一步让模型看到哪些 token | 单步 context window |
| Harness engineering | 循环、工具、context 策略、权限、校验 | 整次运行，跨步骤跨会话 |

`harness engineering` 这个词是 2026 年初才流行开的，比 prompt → context engineering 晚一层。所以最近才看到满屏都是它，不是它突然被发明，是最近才被命名。

## 四、把前几轮的东西放进同一个坐标系

### 结论

RAG、LLM Wiki、HNSW、context rot、compaction，全在同一个坐标系里。先把「记忆分三层」摆出来：

| 层 | 载体 | 谁维护 |
| --- | --- | --- |
| 权重里的知识 | 参数，训练时冻结 | 训练方，你改不了 |
| 工作记忆 | context window，稀缺、会 rot | harness 每次调用现拼 |
| 长期状态 | 文件系统、session DB、进度文件 | harness，软件维护，模型完全不碰 |

于是这几轮的东西全对上号了：

* **RAG** = 查询时，把外部知识临时塞进工作记忆
* **LLM Wiki** = 编译时，把知识写成文件，靠 index 路由进工作记忆
* **HNSW / IVF** = 塞之前，怎么在百万候选里快速挑出该塞哪些
* **Compaction** = 工作记忆快满时，把旧内容摘要后**卸载到长期状态**
* **Ralph Loop** = 直接换一个干净 context 重来，但状态从文件读回来

同一个矛盾：**context 是稀缺资源，harness 负责调度什么进、什么出。** 模型从头到尾没参与，它只是每次收到一串 token。

### harness 的代价（别只记好处）

* **不确定性叠加**：N 步循环，单步 95% 可靠，整体就按指数衰减。20 步下 $0.95^{20} \approx 0.36$，$0.99^{20} \approx 0.82$——两个「看起来差不多」的单步可靠性，跑 20 步差出一倍多。所以必须有校验门，不能靠模型自己说「完成了」。
* **context 膨胀与成本**：每轮工具结果都往回塞，重读成本随轮数线性涨。
* **失败面变大**：工具、权限、重试、超时、压缩，每一处都能独立出错。
* **被包的对象是非确定性的**：这是 harness 区别于普通运行时最根本的一点——**必须为「模型编造了一个动作」「谎报任务完成」设计优雅降级**，不能假设它诚实。

## 五、工程实践：从崩溃日志反推缺失的运行时资源

### 结论

Electron 应用启动报 `ENOENT`、缺的是安装目录里的资源（不是用户配置）时，正确顺序是：**读崩溃堆栈 → 去源码里确认这条依赖是硬约束还是软失败 → 找官方校验清单 → 最小侵入恢复 → 实测验证**。不要先点「禁用插件」或「重装」，那是绕过不是修复。

### 难点一：`ENOENT` 的路径是推导出来的，不是写死的

现象是启动即崩，报缺一个 skill 描述文件。但真要看懂，得回答「这个路径是怎么算出来的」。答案在两层：

```
主进程：primaryRuntime = resources/runtime/primary-runtime
插件装配：assetRoot = join(dirname(config.source), "office-skills")
```

也就是说 `office-skills` 是 `primary-runtime` 的**同级目录**，路径由 `primary-runtime` 的位置反推而来。所以看到「缺一个 Markdown」时，别只补那一个文件——先看它的**同级目录整体在不在**。这次现场是整个 `runtime` 目录都空了，补一个文件没用。

### 难点二：区分「硬约束」与「软失败」

主进程源码里那句注释是关键证据：提供 primaryRuntime 时，**缺失同级 office-skills 资源会导致 Host 启动失败**。这说明它不是可降级的可选依赖，而是启动前置条件——这决定了「能不能靠禁用插件绕过」的答案是否定的（禁用只是不加载插件，Host 仍然要读这个目录）。

**可复用判断**：崩溃点在 `apply()` / 启动装配阶段、且是同步 `readFileSync`，基本就是硬约束；如果是运行中按需读取再失败，才是软失败。

### 难点三：凭什么相信补进去的文件是对的

这是整个修复里最值钱的一步。asar 包里带了一份 `desktop-runtime.json`，是 21046 条文件的官方清单，每条都带 `bytes` 和 `sha256`。做法是：

1. 从 asar 里按 offset 提取原始文件
2. 用清单里对应的 sha256 逐个比对
3. 再按插件的解析逻辑（frontmatter + `description` 字段）模拟校验一遍

8 个资源文件全部一致、7 个描述文件全部解析通过，这才叫「补对了」。**没有校验清单时不要凭文件名猜内容**——版本一升级，猜出来的东西就是定时炸弹。

### 难点四：验证要能被观测，不能靠「应该好了」

验证方式是启动进程后等待固定时间，检查三件事：进程数是否存活、崩溃日志是否新增、主窗口标题是否出现。三项都是可观测事实，而不是「看起来没报错」。

顺带一个 Windows 上的实操坑：`tasklist /v` 遍历全部窗口标题会卡到超时，枚举可见窗口应该直接调 Win32 的 `EnumWindows` + `GetWindowTextW`，快得多。

### 遗留风险要主动说出来

只补了 `office-skills`，`primary-runtime`（bundled node / pnpm / python 加 node\_modules）仍是空的。启动和普通对话不受影响，但真正调用「渲染 / 重算 / 导出 PDF」这几个 skill 时会去找 `primary-runtime/dependencies/node/bin/node.exe`，那时才报错。

**这是「修好了」和「修彻底了」的区别**：能让它起来，不等于所有路径都能走通。报喜之前先把没走通的那条路标出来。

## 六、云厂商免费层：额度口径与注册风控

### 结论

「永久免费」和「半年试用」是两种完全不同的东西，注册被拒也几乎从来不是单一原因。先把两家的性质分清，再谈注册技巧。

| ‍ | Oracle Always Free | AWS Free plan |
| --- | --- | --- |
| 花钱 | 0 | 0 |
| 能用多久 | 永久（只要不闲置） | 6 个月，或 credits 用完即止 |
| 到期后 | 闲置回收实例；账号约 30 天闲置可能暂停 | 账户关闭，数据保留 90 天后删除 |
| 典型配置 | ARM 2 OCPU + 12 GB | t3.micro 1 GB（t3.small 2 GB 要花 credits） |
| 注册难度 | 极高 | 中高 |

AWS 那 200 美元不是「永久免费 VPS」，是半年试用装。想长期挂博客和常驻服务，它从设计上就不是干这个的——半年后要么付钱，要么搬家。

### 口径地雷：厂商自己的文档互相矛盾

Oracle 的 ARM 额度，资源清单页写的是 **2 OCPU + 12 GB**，但总览页、英文 FAQ、Resource Reference 上仍写着 4 OCPU + 24 GB。同一家厂商、同一个时间点、不同页面口径不一致。

**结论性做法**：引用**资源清单页**（Always Free Resources），并主动说明这处矛盾。否则会按四年前的教程去期待 4C24G，然后在「为什么只能开 2 核」上浪费半天。

### ABC 到底是什么

「ABC」不是玄学黑话，是注册提交后官方错误页的三条原文：

* (a) 使用的是预付卡。Oracle 仅接受信用卡和借记卡
* (b) 有意或无意遮挡了人员地点或身份信息
* (c) 输入的信息不完整或不准确

所以「避免 ABC」就是把这三条逐条掐死。附带一个高频死因：「尝试创建多个账户」——同一张卡、同一手机号、同一邮箱重复注册直接拒。

### 风控排查的正确优先级

社区指南动辄列十几条原因，看完也不知道先查哪个。按权重排，前两位是：

1. **网络环境**。IP 归属类型是头号杀手——机房段（AWS、GCP、Azure、OVH 这类 ISP 名）权重最高，开 VPN 切美国反而直接触发拒绝。要的是住宅宽带，且代理所在国家与注册区域一致。
2. **支付方式**。接受信用卡和「功能类似信用卡的借记卡」，**不接受带 PIN 的借记卡和一次性虚拟预付卡**。
3. 身份信息一致性：姓名、地址、邮箱、手机号能否互相对上。
4. 注册行为：同一 IP 试过几次、浏览器指纹、操作节奏。
5. 区域合规：所选区域对该国是否开放免费注册。

### 一个能直接定位问题的判据

提交后看**卡上有没有预授权记录**，这一条比任何猜测都准：

| 现象 | 说明 | 怎么办 |
| --- | --- | --- |
| 有预授权但注册失败 | 卡侧问题 | 换发卡行，或逐字对齐账单地址 |
| 连小额预授权都没冻到就失败 | 请求在支付网关之前就被毙了 | **换卡没用**，去查网络、浏览器环境、信息一致性 |

第二条是最容易被误判的：失败就换卡，换三张还是失败，因为问题根本不在卡上。

### 两个不可逆的坑

* **Home Region 注册时选定，终生不可改**，没有工单能改，选错只能注销重开。开机器前先想清用途。
* **注册成功后不要注销那张卡**：后续还有二次、三次验证扣款，失败会冻号。
