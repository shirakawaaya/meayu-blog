## **一、文档分块**

分块是整条链路的地基。块切得不对，后面向量化、召回、重排再精细也救不回来——因为答案所在的上下文已经被切碎了。

### **1.1 五种主流策略**

**① 固定分块 + 滑动窗口**

按固定字符数或 token 数切，相邻块之间保留一段重叠（overlap）。最简单的做法，实现成本几乎为零。

缺点是它完全不看语义边界：一句话可能被切在两块中间，一个条款可能被劈成两半。重叠窗口是为了缓解这个问题——让被切断的内容在两块里都出现一次，至少有一块能检索到。

适合：结构松散、没有明显标记的纯文本，比如会议记录、访谈稿。

**② 递归分块**

按优先级依次尝试分隔符：先按段落（`\n\n`）切，段落还太长就按换行切，再长就按句号切，最后才退到固定长度。

它比固定分块聪明的地方在于「尽量在自然边界断开」。LangChain 的 `RecursiveCharacterTextSplitter` 就是这个思路。

适合：新闻、博客、说明文档这类段落结构清晰的文本。

**③ 结构感知分块**

直接利用文档自身的结构标记：「第一章」「第二条」「一、」「（一）」。块边界就是结构边界，每个块自带层级信息（章 → 节 → 条）。

这是制度、法规、标准这类文本的最优解——因为这类文档的语义单位本来就是「条」，一条一个完整规定。

适合：法律条文、规章制度、技术标准、合同。

**④ 父子块（Small-to-Big）**

索引时用小块（子块）做向量化，保证检索精度——块越小，向量越聚焦，越不容易被无关内容稀释；命中后再返回它所属的大块（父块），保证上下文完整。

这是「检索精度」和「生成上下文」两个目标的解耦。代价是要维护两套块的映射关系，存储翻倍。

**⑤ 语义分块**

用 LLM 或嵌入模型判断语义边界：把相邻句子做向量化，计算相似度，相似度骤降的地方就是话题切换点。

效果最好，但成本也最高——一份长文档可能要几十次模型调用，而且结果不稳定（同一份文档跑两次可能切得不一样）。

适合：结构混乱但语义连贯的长文本，且预算充足。

### **1.2 我们项目的选择**

用的是 **③ 结构感知 + 三级降级链**：

```
有「第X条」 → 按条款切（ArticleChunker）
没有条款但有「一、」「（一）」 → 按小节切（SectionChunker）
两者都没有 → 按段落聚合（ParagraphChunker）
```

为什么必须有降级链：实测 166 篇语料里 **45% 的文档没有「第X条」**——实施方案、意见、通知这类文件用的是「一、二、三」的小节结构。只做条款切分，这 45% 会被切成一堆无意义的段落。

最终效果：166 篇切成 3065 片，单文档中位 18 片，片长中位 99 字、P90 312 字。

这里踩过一个真实的坑：公文里存在**运行式标题**——「一、准确把握基本规范。研究生导师是……」标题和正文黏在同一行，中间没有换行。最初把整行当小节名，最长的一条 463 字，直接撑爆了数据库字段。修法是按第一个断句符切开，前半做标题、后半归正文；而断句符在末尾时（「一、为规范管理，制定本办法。」）说明整行本身就是正文，不能当标题，否则这一块的内容会凭空消失。

### **1.3 一个容易被忽略的设计：三份文本分离**

同一份内容在库里存三份，各有各的用途：

**字段内容用途**`content`原文展示、引用`embedding_text`标题 + 章 + 条号 + 正文向量化与分词`content_tokens`jieba 分词结果建 GIN 索引

为什么不能合并：条款往往很短（「本办法自颁布之日起施行。」），单独向量化时几乎没有语义信号。补上标题和条号之后，向量里才带上了「这是哪个文件的第几条」这层信息，短条款才检索得到。

## **二、向量化**

分块之后，每个块要通过嵌入模型转成一个稠密向量。这个向量的每一维都是模型从文本里学到的某种抽象特征，不是人工定义的可解释维度。

**关于「维度越高越精确」这句话，需要补一个限定。**

* 对**同一个模型**来说，原生维度就是它的表达能力上限。bge-m3 是 1024 维，qwen3-vl-embedding-8b 是 4096 维，后者信息容量确实更大。
* 但**跨模型比维度没有意义**。4096 维的小模型可能不如 1024 维的大模型，因为维度只是输出形状，真正决定效果的是训练数据和目标函数。
* **截断维度会掉效果**。我们实测过：给两个模型传 `dimensions: 1024` 参数，都直接报错 `does not support matryoshka representation, changing output dimensions will lead to poor results`。支持 MRL（Matryoshka 表示学习）的模型才能安全降维，这两个不在其中。

所以「维度越高越好」是个过于简化的说法。准确表述是：**在模型原生维度下，信息容量随维度增加；但截断、跨模型比较、以及高维带来的检索开销，都会让这个结论失效。**

## **三、近邻搜索：KNN 与 ANN**

### **3.1 KNN 是精确解**

KNN（k-Nearest Neighbors）要回答的问题是：在这 N 个向量里，哪 k 个离查询向量 A 最近？

精确做法是把 A 和库里**每一个**向量都算一次距离，排序取前 k。结果一定正确，复杂度 O(N·d)——N 是向量条数，d 是维度。

数据量小的时候这没问题。但 N 到百万级、d 到 4096 时，每次查询都要做几十亿次浮点运算，延迟会到秒级甚至分钟级，实际不可用。

我们项目实测过：3065 条 4096 维向量，全表扫描 **1134ms**。查询向量化本身只要 65ms，慢的完全是扫描。

### **3.2 ANN 用精度换速度**

ANN（Approximate Nearest Neighbor）放弃「一定找到最近的」，只要求「找到足够近的」。

思路是：不去碰全部数据，先通过某种索引结构把搜索范围缩小到一个「很可能包含答案」的子集，只在子集里精确比较。大部分明显不相关的向量被直接跳过。

代价是有可能漏掉真正最近的邻居——这叫**召回损失**，是 ANN 的核心指标。工程上追求的是「召回损失足够小、速度快足够多」。

### **3.3 HNSW：分层可导航小世界**

HNSW（Hierarchical Navigable Small World）是目前最常用的 ANN 索引结构。它的做法是建一个**多层图**：

```
第 2 层（最稀疏，只有几个节点，边很长）      ●————————●
                                            |        |
第 1 层（中等密度）                    ●———●———●———●
                                      |   |   |   |
第 0 层（全部节点，边最短）        ●—●—●—●—●—●—●—●—●
```

* **顶层稀疏**：节点少、连接跨度大，相当于「先看地图上的大区域」
* **底层稠密**：包含所有数据点、连接距离近，相当于「在小区里找具体门牌号」

搜索过程是**由粗到细、自上而下**：

1. 从顶层某个入口点开始，在当前层找离目标最近的邻居
2. 一旦发现没有更近的了，就下沉到下一层，以当前点作为新的入口
3. 重复直到最底层，在底层做最后的精确比较

这样每层只需要比较很少的节点，总复杂度从 O(N) 降到大约 O(log N)。

几个可调参数：`m`（每个节点的连接数，越大越准也越占内存）、`ef_construction`（建索引时的候选池大小）、`ef_search`（查询时的候选池大小，可运行时调）。我们建索引用的是 `m=16, ef_construction=64`。

### **3.4 相似度度量**

三种常用方式：

**度量公式直觉特点**余弦相似度看两个向量的**夹角**忽略向量长度，只比方向；取值范围 [-1,1]，越接近 1 越相似内积方向 × 长度长度也会影响结果；若向量已归一化，内积等价于余弦欧氏距离看两点的**直线距离**越接近 0 越相似；对绝对位置敏感

文本检索几乎都用**余弦相似度**，因为文本向量的「长度」往往反映的是文本长短而不是语义强度，这个信息不应该参与相似度计算。

我们用的 bge-m3 和 qwen3-vl-embedding-8b 输出都是 L2 归一化的（实测向量模长约等于 1），所以余弦和内积在这两个模型上是等价的。

pgvector 里余弦距离用 `<=>` 算子，返回的是**距离**（1 - 余弦相似度），所以 `ORDER BY embedding <=> query` 是升序取最近。

## **四、pgvector 的维度限制**

### **4.1 存储和索引是两回事**

这是最容易搞混的地方：

* **存储**：`vector` 类型最多支持 **16000 维**。4096 维完全存得下。
* **索引**：HNSW / IVFFlat 对 `vector` 类型的上限是 **2000 维**，对 `halfvec`（半精度）是 **4000 维**。

这两个限制我都实测验证过：建 `vector(4096)` 的 HNSW 索引报 `column cannot have more than 2000 dimensions`；改用 `halfvec(4096)` 报 `cannot have more than 4000 dimensions`。

### **4.2 为什么会有这个限制**

ANN 索引要在内存里维护图结构和距离缓存。维度越高，单条向量的内存占用越大（4096 维 float32 = 16KB/条），距离计算也越慢。限制维度本质上是为了保证索引能放进内存、查询能在毫秒级完成——是工程取舍，不是 PG 的缺陷。

### **4.3 我们经历过的三次选择**

**第一次：qwen3-vl-embedding-8b（4096 维，无索引）** 能存不能索引，只能全表扫描。实测 P95 990ms，其中 1134ms 是扫描、65ms 是向量化。召回率 92.59%，是所有方案里最高的。

**第二次：二进制量化（技术验证，最终未采用）** pgvector 的 `bit` 类型上限是 64000 维，4096 完全能建索引。做法是把每维浮点数压成 1 个符号位（1 bit），按汉明距离粗排取 top100，再拿原始浮点向量精排。

实测结果很有说服力：

**指标数值**量化 3065 片119ms建 HNSW 索引505ms索引查询 top100**0.5ms**（对比全表扫描 1134ms）二进制直接取 top10召回率 93%二进制 top100 + 精排**召回率 100%**

也就是说，二进制量化能在不换模型、不掉召回的前提下把查询提速两千倍。最终没采用，是因为换一个原生低维的模型能从源头解决问题，不必引入一套额外的量化与精排逻辑。

**第三次：BAAI/bge-m3（1024 维 + HNSW，当前方案）** 1024 维在 2000 上限之内，索引能建。查询 P95 从 990ms 降到 431ms。代价是召回率从 92.59% 掉到 85.19%——这就是「维度换索引」的真实成本。

### **4.4 为什么不用 Milvus / Chroma**

除了你提到的**双写不一致**（业务库和向量库要各自维护一份，任何一边写失败就会出现数据错位，而且没有跨库事务可用），还有一条更硬的理由：**约束下推**。

我们的检索要在 SQL 层过滤受众和时效条件（学生只能看学生条款、已废止的不能召回），这些条件依赖 `kb_document` 表里的 `audience`、`doc_status`、`effective_date` 字段。用 pgvector 时，`kb_chunk` 和 `kb_document` 在同一个库，一句 JOIN 就完成了：

sql

```
FROM kb_chunk c JOIN kb_document d ON d.id = c.doc_id
WHERE (c.audience = 'ALL' OR c.audience = ?) AND d.doc_status = 'ACTIVE'
```

换成独立的向量库，这些标量过滤要么能力弱、要么只能「先召回再过滤」——而先召回再过滤的问题在于：被过滤掉的候选已经污染过排序了。

所以选 pgvector 的真正理由排序是：**约束下推 > 事务一致 > 少一个中间件 > 数据量小**。

## **五、评测指标**

### **5.1 Recall@5（召回率@5）**

前 5 个结果里，包含了多少比例的相关文档。

公式：`命中数 / 应命中总数`。我们的评测集里每题 gold 是一个或多个切片，命中任一即算召回（多跳题会额外统计「两条都召回」的比例）。

**为什么是「底线」**：召回决定了「正确答案有没有进入候选池」。如果 top-5 里根本没有正确条款，后面的重排、生成、引用回填全部无意义。这是整条链路的第一个硬指标。

实测：纯 BM25 51.85%，纯向量 85.19%，融合 88.89%。

### **5.2 MRR（平均倒数排名）**

第一个相关结果出现位置倒数的平均值。

公式：`MRR = (1/|Q|) · Σ (1/rank_i)`，其中 `rank_i` 是第 i 个问题里第一个正确结果的位置。

* 正确结果排第 1 → 得 1 分
* 排第 2 → 0.5 分
* 排第 5 → 0.2 分
* 前 k 名都没出现 → 0 分

**它衡量的不是「有没有找到」，而是「找得多靠前」**。适合有唯一正确答案的问答场景。

和 Recall 的区别：Recall@5 只看「在不在前 5」，MRR 还看「排第几」。两个指标会背离——我们实测就出现了：加 Rerank 后 MRR 从 0.8256 升到 0.8733（头部更准），但 Recall@5 从 88.89% 掉到 85.19%（有正确答案被挤出了前 5）。这种情况说明重排改善了排序质量，但阈值设置把一些候选直接丢弃了。

### **5.3 P95（95 分位延迟）**

把所有请求的耗时排序，第 95% 位置的那个值。含义是「95% 的请求都在这个时间内返回」。

**为什么不用平均延迟**：平均值会被少数极快或极慢的请求拉平，掩盖尾部问题。用户感知最差的是那 5% 的慢请求，P95 正好盯住这部分。

实测：纯 BM25 90ms、纯向量 431ms、融合 505ms、加 Rerank 1133ms。

### **5.4 我们额外需要的两个指标**

**拒答准确率**：不该答的问题里，有多少比例正确拒答了。这是「宁可拒答，不可错答」这条原则的量化。评测集里专门设计了 3 道无答案题（问制度里确实没规定的事），用来测这一项。

**引用准确率**：回答里的 `[编号]` 有多少能对应到真实证据切片。这个可以完全在代码里硬判——解析引用编号，检查是否落在证据集范围内，不需要人工标注。

## **六、模型选型**

### **6.1 为什么是 BGE 家族**

BAAI（智源研究院）的 BGE 系列在中文检索任务（C-MTEB 榜单）上长期排在前列，且开源、可私有部署、维度规整。对我们这种中文制度文本的场景，比通用多语言模型更对口。

### **6.2 三个模型的分工**

**模型类型维度作用**BAAI/bge-m3Embedding1024主力向量模型，支持稠密/稀疏/多向量三种输出BAAI/bge-large-zh-v1.5Embedding1024备用，同维度可互为降级BAAI/bge-reranker-v2-m3Rerank—对「问题—原文」配对打分，做精排

两个 embedding 都是 1024 维，这一点很重要——**同能力的候选必须维度一致**，否则主模型挂了降级到另一个，写进库的向量维度就变了，检索时直接 SQL 报错。

### **6.3 Rerank 不是无脑加分**

这是我们踩到的反直觉结论。加 Rerank 之后：

**指标不加加**Recall@588.89%85.19% ↓MRR0.82560.8733 ↑多跳双召回66.7%33.3% ↓↓

原因有两个：

1. **重排是逐片打分的**。多跳题需要两条来自不同文档的证据，重排器只对单片判断相关性，其中一条常被压低。
2. **阈值 τ 会直接丢弃低分片**。现在 τ=0.2 是拍的，没有调过。

所以 Rerank 默认关闭，等阈值调好再开。

## **七、工程化：多供应商抽象与高可用**

### **7.1 为什么要抽象**

单个供应商的问题：换模型要改代码、一家挂了整条链路挂、做模型对比实验要改代码重编译。抽象之后，换模型只改配置。

### **7.2 三个端口**

按**能力**而不是按供应商划分：

* `ChatPort`：对话与流式
* `EmbeddingPort`：向量化
* `RerankPort`：重排

每个端口有多个 OpenAI 兼容协议的实现。调用方只说「我要向量化」，由 `ModelRegistry` 决定用哪家、哪个模型、失败了换谁。

### **7.3 三态熔断**

`ModelHealthStore` 维护每个模型的健康状态：

代码块

```
CLOSED（正常） --连续失败N次--> OPEN（拒绝调用）
                                  |
                            等待 openDurationMs
                                  ↓
                           HALF_OPEN（放一次探测）
                              /        \
                        成功 /          \ 失败
                            ↓            ↓
                        CLOSED         OPEN
```

阈值和熔断时长可配（默认连续 3 次失败、熔断 30 秒）。自研而不引 Resilience4j 的理由：只需要三态状态机这一个能力，不需要舱壁、限流、指标导出，一百行能说清楚，也少一个依赖。

### **7.4 降级策略**

按能力区分，不是一刀切：

* **Chat 失败** → 按优先级换下一个模型；全部失败才报错
* **Embedding 失败** → 向量通道降级为纯关键词检索（`HybridRetriever` 捕获异常后继续）
* **Rerank 失败** → 直通，用融合排序的结果

核心原则：**辅助手段挂了不能拖垮主流程**。

### **7.5 SSE 流式**

一次性返回的问题是大模型生成动辄十几秒，用户面对白屏。SSE 把输出拆成事件流：

```
event: meta   → 引用列表（先渲染引用卡片）
event: delta  → 正文增量（逐字显示）
event: done   → messageId、耗时
event: error  → 出错时先发再关连接
```

先推 `meta` 是关键设计：用户在等正文的时候，引用卡片已经能看到，心理等待时间大幅缩短。

流式失败的处理也有讲究：**只要还没吐出第一个字，就允许换下一个候选模型；已经吐出内容再失败就中止，不重来**——否则用户会看到半句话突然从头开始。

## **八、问答链路的三个增强**

参考 `nageoffer/ragent` 的 `StreamChatPipeline`（九个阶段、短路返回、上下文对象贯穿）做了适配。

### **8.1 记忆加载**

从 `chat_message` 表读最近 3 轮对话，格式化成「用户：…」「助手：…」拼进改写 Prompt。

为什么只读最近 N 轮而不是全量：制度问答的追问通常紧接上一轮，更早的内容既占上下文又容易让改写跑偏。

### **8.2 问题改写**

把口语化的、带省略的问题改写成适合检索的完整问句。

实测最有力的证据是一组两轮对话：

**轮次问题结果**第 1 轮我现在大二，还能申请转专业吗？引用第五条、第七条第 2 轮那大三呢？引用第七条

「那大三呢」这五个字本身检索不到任何条款。靠记忆把它补成「大三学生申请转专业」，才命中第七条「大三及以上学生原则上不得转专业」。

### **8.3 意图识别**

判断问题是「查制度」还是「闲聊」。判为闲聊就直接回固定话术，不走向量召回。

和改写合成**一次模型调用**完成——两者用的上下文完全一样，合成一个 Prompt 出结构化 JSON 更划算：

json

```
{"intent":"RAG","rewritten":"大三学生申请转专业的规定"}
```

实测「你好」在 1.2 秒内返回拒答，而正常问答要 3~5 秒。

### **8.4 三道拒答闸门**

**闸门触发条件动作**检索闸召回为空，或最高分低于阈值不进模型，直接拒答证据闸回答里没有可解析的引用编号重生成一次，仍不合格则拒答时效闸引用到已废止文档拦截并提示最新版本

关键点：**拒答判断放在代码里，不只靠 Prompt**。Prompt 能降低编造概率但保证不了；而「引用编号能否解析回证据」是可以在代码里硬判的事实。
