## 今日速览（结论先行）

今天两条主线：一是**基础设施的概念地图**（服务器 / 云 / VPS / IP / 域名 / Cloudflare / 短链），二是**知识库方案的全景与选型**（RAG → Advanced RAG → GraphRAG → LLM Wiki）。

三条最值得记住的结论：

1. **基础设施那一串名词，本质是一条链上的不同环节**：服务器是机器，云是出租机器，VPS 是分租的一间房，IP 是门牌号，域名是名字，DNS 是通讯录，Cloudflare 是前台 + 保安，短链是临时化名。
2. **知识库方案的分水岭只有一个问题**：这份知识是在什么时刻被加工成「能塞进 context 的形状」的？——查询时（RAG）、索引时（GraphRAG/LightRAG）、编译时（LLM Wiki）、不加工（长上下文直读）。
3. **RAG 没有死，它降级了**：从一个「架构」降级成「agent 手里的一个工具」，和 SQL、API 调用、文件读取平级。2026 年的正确问法是 context engineering，不是 RAG vs 长上下文的二元论。

## 一、基础设施概念地图

### 1.1 先钉住一句话锚点

> **服务器是电脑本身，云是出租这种电脑的生意，VPS 是分租出去的一间房，IP 是地址，域名是名字，Cloudflare 是大楼前台 + 保安，短链是临时的化名跳转。**

后面所有名词都能对号入座。

### 1.2 服务器 vs 云

* **服务器**：一台 24 小时开机的电脑，没显示器而已。跑操作系统，上面跑数据库、网站、文件服务。
* **云**：不是一台新机器，是**商业模式 + 虚拟化规模化**。以前公司自己买物理机放机房；现在需求太多，就把海量物理机统一管理、按小时租出去。

  + 公有云 = 阿里云 / 腾讯云 / AWS，谁都能租。
  + 私有云 = 只有一家公司内部用。

### 1.3 VPS 与隔离度的权衡

一台物理机很强，别浪费它 → 用虚拟化切成几十份，每份有独立 CPU / 内存 / 硬盘 / 系统，对外看起来像一台独立服务器，这就是 VPS。

| 类型 | 隔离度 | 成本 | 适合 |
| --- | --- | --- | --- |
| 物理机 / 裸金属 | 最高，整台归你 | 高 | 大企业，对性能极度敏感 |
| VPS | 中，虚拟机隔离 | 中低 | 个人网站、跑服务、学习 |
| 共享主机 | 低，共用一个系统 | 最低 | 几乎没定制需求的小站 |
| 容器 (Docker) | 更细，进程级隔离 | 最灵活 | 微服务、开发部署 |

所谓「买个 VPS 搭站」，就是第三行。隔离度越低越便宜，代价是「邻居吵架会吵到你」。

### 1.4 IP：机器的地址

* **公网 IP**：全世界唯一，真实门牌号，别人能通过它找到你。
* **私网 IP**：`10.x`、`172.16.x`、`192.168.x`，局域网内部用，出不了门，靠 NAT 转发出去。

IPv4 是 32 位，约 43 亿个，早就不够用；IPv6 是 128 位，地址多到随便发。租 VPS 商家一定给你一个公网 IP，否则别人找不到你。

### 1.5 域名与 DNS：名字和通讯录

IP 是数字，记不住，而且换服务器就变。所以有了**域名**（`example.com`，给人看的名字），再有了 **DNS**（翻译官：输入域名 → 查出对应 IP → 浏览器拿到 IP 才去连接）。

分级这样看就够：`www.example.com` 里 `com` 是顶级域名（后缀），`example.com` 是你注册的主域名，`www` 只是子域名。注册域名后要去注册商那里把 DNS 指向服务器 IP，这一步叫**域名解析**。

> 比喻：**IP 是电话号码，域名是通讯录里的名字，DNS 是通讯录。**

### 1.6 Cloudflare：它至少干三件事

1. **DNS 托管**：帮你做上面的解析。
2. **CDN 缓存**：全球几百个节点，图片 / 文件先缓存一份在节点上，用户访问就近节点，更快。
3. **反向代理 + 防火墙**（关键）：用户请求先到 Cloudflare，再由 CF 转发到你的 VPS，这一步叫**回源**。

```
你(用户) -> 域名解析 -> Cloudflare 节点(IP) -> (回源) -> 你的 VPS(IP) -> 返回网站
```

好处：源站 IP 被隐藏、免费 SSL、挡 DDoS、全球加速。  
代价：流量要过它一遍、完全依赖它、免费版有速率限制、它对哪些国家 / 地区解封直接决定你的可用性。

判断方法：你看到的 IP 如果是 Cloudflare 的 IP，说明那台站挂了 CF；不是，就是直连源站。

### 1.7 短链：化名那套

短链服务就是一张**映射表**：长链接 `https://example.com/a/very/long/path?id=123` 存进数据库，分配短码 `aB3x`，生成 `https://short.example/aB3x`。访问短链 → 服务器查表 → 回 `302` 重定向 → 浏览器自动跳过去。

为什么需要：传播好看（短信 / 二维码不爆长度）、可统计点击、后台能改指向而不用改到处发出去的东西。  
代价：多一跳；短链服务一关，链接全死。

### 1.8 难点举例：一个能验真的问题

**问：Cloudflare 节点全挂了，你的 VPS 还开着，别人能直接用 IP 访问你的网站吗？**

**答：能。** DNS 只是「名字 → IP」的翻译，绕过翻译直接敲 IP，请求就直连源站了。

**除非**你在源站防火墙做了 IP 白名单，只放行 Cloudflare 的网段——这才是正确配置，也是「CF 隐藏源站」真正的意义所在。

所以「用了 Cloudflare 就安全」是个**错觉**：源站 IP 一旦泄露、又没白名单，攻击者绕过 CF 直打你的 VPS，防护全废。这就是很多人被 DDoS 打穿的真正原因。

### 1.9 整条主干串起来

> 买一台 VPS → 拿到公网 IP → 在自己域名上把 DNS 解析到这个 IP →（可选）把 DNS 交给 Cloudflare 接管 → 部署网站 → 要分享就用短链生成易记跳转

容器、Kubernetes 这些，都是在 VPS 这一层之上再套的东西。

## 二、知识库方案全景：按「加工时刻」分类

### 2.1 先建直觉：这一整类方案在解什么矛盾

模型的权重是**冻结**的。你训完那天，它就再也不知道新东西了。但你的知识是**活的**——今天看的论文、昨天踩的坑、公司内部的 SOP。

*公司内部的* ***SOP*** *指* ***Standard Operating Procedure，标准作业程序/标准操作规程****。*

*简单说，就是把某项工作“怎么做”的标准步骤写清楚，让不同人按同一套方法执行，保证结果稳定、可追溯、可培训。*

于是只剩一个办法：**在生成的那一刻，把相关信息塞进 context**。

所以所有方案唯一的差别只有一个问题：

> **这份知识，是在什么时刻被加工成「能被塞进 context 的形状」的？**

| 加工时刻 | 方案 | 本质 |
| --- | --- | --- |
| 查询时 | Naive / Advanced / Agentic RAG | 现查现取，知识保持原始形态 |
| 索引时 | GraphRAG / LightRAG | 建库时预先抽成图结构，查询时走关系 |
| 编译时 | LLM Wiki、RAPTOR 摘要树 | 入库时直接写成成品文章，查询时只读成品 |
| 不加工 | 长上下文直读 | 全塞进去，让模型自己找 |

记住这张表，后面所有争论都能自己定位。

### 2.2 Naive RAG 的四个致命伤（「RAG 已死」真正的靶子）

流水线：**切块 → 嵌入 → 向量检索 top-k → 拼进 prompt**。

1. **切块切断语义**。一页文档切成 512 token，第 3 块开头写「如上所述，该参数需设为 0」——「如上」已经在上一个块里了。检索到这一块，模型看到的是残缺句子。
2. **语义相似 ≠ 答案相关**。向量只认「字面意思像」，不认「这真的回答了问题」。问「退款多久到账」，它能召回三段讲「退款政策精神」的废话，却不给你那句「3-5 个工作日」。
3. **精确匹配全废**。查错误码 `TS-999`、查订单号、查函数名，向量检索基本瞎——而这恰恰是企业里最高频的查询。
4. **多跳直接崩**。问「A 公司 CEO 的母校在哪」，需要先找 CEO 再找母校，单次向量检索拿不到这条链。

### 2.3 Advanced RAG：工程师拿命补的四个补丁

按「便宜到贵、收益从大到小」的顺序加：

**补丁一：混合检索（Hybrid + RRF）**  
向量（dense）负责语义，BM25（稀疏）负责精确词，两路并行，用 Reciprocal Rank Fusion 融合排名。  
一句话：**语义靠向量，精确靠 BM25，两边都要**。这是 2026 年生产环境的**基线配置**，不是高级技巧。

**补丁二：重排（Reranker）**  
粗排捞 100–150 个候选，再用 cross-encoder 精排取前 10–20。  
为什么有效：向量检索是「query 和 doc 各自独立编码再算距离」；reranker 是「query 和 doc 一起送进模型打分」——后者准得多，代价是慢。

**补丁三：Contextual Retrieval（Anthropic 的招牌）**  
切块之前，先让 LLM 给每块生成一句 50–100 token 的块级上下文说明，**拼在块前面**再嵌入、再建 BM25 索引。解决的正是 2.2 的第一个伤：那块现在有了「这段出自 XX 文档第 3 章，讲退款时效」的前缀。

Anthropic 官方数字（top-20 检索失败率，可直接当面试弹药）：

| 配置 | 失败率 | 相对下降 |
| --- | --- | --- |
| 基线 RAG | 5.7% | — |
| • Contextual Embeddings | 3.7% | 35% |
| • Contextual BM25（混合） | 2.9% | 49% |
| • Reranking | 1.9% | 67% |

**补丁四：查询侧改造**

* **Multi-query**：一个问法扩成 5 个变体，都检索，取并集。
* **HyDE**：先让模型凭空写一段「假答案」，用假答案去检索。适合口语化问法；但对精确数值 / 实体查询要慎用。
* **Small-to-Big / Parent-Child**：用小块检索保精度，但**返回它所属的大块**给模型保上下文。这是切块矛盾的正解，便宜、性价比极高。

### 2.4 RAPTOR：索引时就写好摘要树

把文档聚类、递归摘要，自底向上长成一棵树。查询时既能命中叶子细节，也能命中顶层概括。

它已经不只是检索——它在**入库时就替你做了一次理解**。这个思路再往前一步，就是 LLM Wiki。Wiki 本质上是一个**可由多人协作编辑的网站或知识库**。

### 2.5 Agentic RAG：2026 年真正的答案

不再「检索一次就完事」，而是**把检索变成 agent 的一个工具**：

```
模型判断「我需要查资料」
  → 决定查哪个库（向量库？SQL？文件系统？API？）
  → 执行检索
  → 自己评估「这够回答吗？不够」
  → 改写 query，再查一轮
  → 够了 → 生成
```

关键变化：**控制权从流水线转移到模型手里**。检索次数、检索目标、要不要重试，全由模型在推理过程中决定。

一个反直觉但重要的事实：**顶级编码 agent（Claude Code 那类）根本不用向量数据库，它们用 grep / ripgrep**。因为搜「`processPayment` 在哪定义」，正则精确匹配比向量相似度好一万倍。这是「检索」回归「按查询模式选工具」的标志性事件。

## 三、GraphRAG 家族：为什么要建图

### 3.1 它解决的是向量检索的「结构性无能」

向量检索的问题不是「不够准」，是**它压根看不见关系**。

* 问「这个法规条款后来被哪条修订了」——这是引用链，是边，不是相似度。
* 问「供应链里哪个环节最脆弱」——需要沿关系走三四跳。

**知识图谱就是把这些边显式存下来。** 图遍历是确定性的：A → B → C，一步不漏。这是向量检索永远做不到的事。

### 3.2 微软 GraphRAG 的三段流水线

```
原始文档
  ↓ LLM 抽取实体 + 关系（贵，这一步是大头）
知识图谱
  ↓ Leiden 社区发现（把密集连接的节点聚成「社区」）
社区层级结构
  ↓ 每个社区让 LLM 写一份「社区报告」（摘要）
预生成的全局摘要
  ↓ 查询时
Local Search / Global Search / DRIFT Search
```

三种检索模式，一句话记：

* **Local**：从某个实体出发，取它的邻居和相关原文片段。答「某个具体人 / 物是什么」。
* **Global**：用社区报告做全局主题总结。答「这批文档整体在讲什么」。**这是纯 RAG 完全给不出的能力**——因为答案不存在于任何一个 chunk 里。
* **DRIFT**：Local 和 Global 的混合，先宽后窄。

### 3.3 代价，以及社区为什么集体造反

GraphRAG 的贵是**灾难级**的：全库实体抽取 + 全量社区摘要，一次索引可能烧掉几百美元；文档更新一次，社区要重划，索引要重建。

| 方案 | 造反方式 | 关键机制 |
| --- | --- | --- |
| LazyGraphRAG（微软自家） | 把索引成本压到 GraphRAG 的 0.1% | 建库时不预生成摘要，把「理解」推迟到查询时按需做 |
| LightRAG | 不划社区，只存实体-关系图 | 双层检索：低层查具体实体（具象关键词），高层查抽象主题（抽象关键词）；支持增量更新，新文档直接合并节点和边 |
| PathRAG | 在 LightRAG 上加路径剪枝 | DFS 取 3 跳邻居，再按「资源分配」剪掉低权重分支，只留关键关系路径 |

### 3.4 必须泼的一盆冷水

社区宣传的数字（LightRAG 比 GraphRAG 省 99% API 调用、12 倍成本）是**厂商口径**。

更值得警惕的是一个 2025 年的元分析：**把评估偏差（位置偏差、长度偏差、试验偏差）控制掉之后，GraphRAG 类方案的增益大幅缩水，LightRAG 对 naive RAG 的 72% 胜率甚至反转成 naive 略优。** 在通用查询分布上，真实增益常在 10% 以内。

> **结论：图的收益高度依赖「你的查询是不是真的需要走关系」。** 用户都在问「这个条款被谁修订过」「这个 bug 的上游依赖是谁」，图就是刚需；只是「找找相关文档」，图是纯浪费钱。

## 四、LLM Wiki：Karpathy 的反向方案

2026 年 4 月 3 日 Karpathy 发了个 gist，引爆一轮「绕开 RAG」的讨论。原话大意：**「我本以为得上 fancy RAG，结果 LLM 自己维护 index 文件维护得挺好。」**

### 4.1 核心翻转：从「查询时检索」到「编译时写完」

| ‍ | RAG | LLM Wiki |
| --- | --- | --- |
| 知识形态 | 原始 chunk，永远原样 | 已被 LLM 写成的结构化文章 |
| 每次提问 | 从零重新检索、重新理解 | 直接读成品，交叉引用已经在那儿 |
| 矛盾处理 | 无（两段矛盾内容同时塞进 prompt 让模型自己纠结） | 入库时就标记了矛盾 |
| 可读性 | 向量库，黑盒 | 纯 markdown，能读能改能 git diff |
| 成本曲线 | 每查一次付一次 | 编译一次，之后近乎免费 |

这就是「**复利**」的具体含义：知识不是每次被重新发现，而是**累积**。加一个新来源，它不是被「索引起来」，而是被**读进去、融进去、改写了已有的页面**。

### 4.2 三层结构（Karpathy 原版）

```
raw/        <- 不可变的原始素材（网页、PDF、访谈），只读
wiki/       <- LLM 编译出的实体页 / 概念页 / 对比页，带 [[wikilinks]]
index.md    <- 目录，故意控制在一屏之内，能整个塞进 context
```

查询时，agent **先读** `index.md`，判断该看哪几页，然后直接读那几页原文。没有向量库，没有 chunk。

### 4.3 它的边界，必须说清楚

**赢的地方**：个人规模（几十到几百页）、知识高度结构化、你要能读懂能改、需要版本追溯。token 效率极高，因为 index 本身就是压缩过的。

**输的地方**：

* **规模天花板**。知识量超过 context 承受能力时，还是得上嵌入。Karpathy 自己也把它限定在「个人研究者」范围。
* **强依赖人工策展**。得有人决定「这个来源值得入库吗」「这条该合并到哪一页」。全自动会退化成垃圾堆。
* **多用户 + 动态权限完全不行**。企业里「这个文件 HR 能看、销售不能看」，markdown 目录做不了 ACL。

## 五、「RAG 已死」：三个论点，一个结论

这个标题底下混着三个完全不同的论证，成立度天差地别，必须拆开看：

### 论点一：「百万 token 窗口取代检索」——部分对，被成本打回

诚实的部分：**在「单文档、小语料、深度跨文档推理」这三类任务上，直接全塞确实赢过 RAG**。这不是情怀问题，是实测结论。

打回来的部分，算三笔账：

1. **重读成本**。250k token 的手册，你问 100 个问题，就是把同一份手册**重读 100 遍**；RAG 只读命中的 2k。差两个数量级。
2. **延迟**。没人愿意等 30 秒。
3. **Context rot（上下文腐化）**。最容易被忽略的一条：**广告的窗口大小 ≠ 可靠可用的窗口**。窗口拉到 1M，长上下文里中段的召回准确率会明显掉。所以「1M 窗口」从来不等于「塞 1M 进去还答得准」。

### 论点二：「naive RAG 死了」——完全对

切块 → 嵌入 → top-5 那条流水线确实该进博物馆。但**它的死因不是长上下文，是它自己太粗糙**——上面那四个补丁就是它的死因证明。

### 论点三：「选择后再读不算 RAG，所以 RAG 死了」——文字游戏

哪怕「RAG 已死」派最爱的 agentic 模式——agent 先 grep 定位文件、再读、再决定要不要再搜——**这也是「先选后读」，也就是检索**。换个名字不改变本质。

### 真正的结论

> **RAG 没有死，它降级了。** 从「一个架构」降级成「agent 手里的一个工具」，和 SQL、API 调用、文件读取平级。

2026 年的正确问法不是「RAG 还是长上下文」，而是：

> **这个 agent，在推理的哪一步，该用哪种检索机制，花多少 token 预算？**

这就是所谓的 **context engineering**——它不是一个新框架，是把这场二元论架空了。

**生产环境的实际默认配置**（记住这条）：**慷慨检索 + 长上下文推理**。不再把 top-5 硬挤进窄 prompt，而是捞几十上百个候选、重排、**然后交给长上下文模型在这堆材料里推理**。检索负责「别漏」，长上下文负责「想明白」。

## 六、选型决策框架

```
你的知识量级？
├─ 个人 / 几十~几百页，结构清晰，要能读能改
│   → LLM Wiki（最省，复利最强）
│
├─ 中等（几千~几万块），更新频繁
│   ├─ 查询以「找相关文档」为主 → Advanced RAG（Hybrid + Reranker + Parent-Child）
│   └─ 查询需要多跳 / 关系 / 审计链 → LightRAG（增量友好，比 GraphRAG 便宜）
│
├─ 大（百万级 chunk），多用户，动态权限
│   → Advanced RAG + 向量库（Qdrant/Milvus）+ 权限同步 + 评估 harness
│   → 多跳占比高再加图（GraphRAG 或 LazyGraphRAG）
│
└─ 单文档深度分析 / 一次性任务
    → 长上下文直读，别建任何库
```

**比选框架更有用的，是「什么查询配什么机制」这张对照表：**

| 查询类型 | 首选机制 |
| --- | --- |
| 「找关于 X 的文档」 | 向量 + BM25 混合 |
| 「`TS-999` 这个错误码什么意思」 | BM25 / grep（精确匹配） |
| 「这段出自哪个文档哪一章」 | Contextual Retrieval + 元数据过滤 |
| 「A 的 CEO 的母校」 | 图遍历 或 Agentic 多轮 |
| 「这批文档整体在讲什么」 | GraphRAG Global / 预生成摘要 |
| 「哪条法规被哪条修订过」 | 图（这是图的唯一刚需场景） |
| 「帮我在这个 repo 里改这个 bug」 | grep + agentic 多轮 |

## 七、落到自己身上的实操建议

当前情况：Obsidian 笔记库 + 秋招知识体系（八股、题解、项目复盘）+ 每天对话自动写 Notion。

**别上向量库。** 规模远没到需要它，而且知识是**高度结构化**的（按学科、按题型、按项目），这正是 LLM Wiki 的主场。

建议顺序：

1. **先做 LLM Wiki**：`raw/` 放原始笔记和题解，`index.md` 做目录，agent 编译成 `concepts/` 实体页。成本几乎为零，能直接读、能 git 管。
2. **加一层 hybrid 检索兜底**：等几百页、index 塞不进 context 了，再给 wiki 加 BM25（`ripgrep` 就够，不用向量库）。
3. **图只在需要时上**：等真的开始问「这几个知识点之间的依赖关系是什么」「这个考点是哪个项目的延伸」，再把概念页的关系抽成图。现在上 GraphRAG 是纯烧钱。

## 附二：今日工程排查记录（非知识学习，备查）

晚上修 Notion 笔记任务时踩的三类坑，与内容学习无关，但概念值得留一笔：

**坑一：MCP 连上 ≠ 授权通过。** Hermes 里「Connectors 连上 Notion」只代表知道去调这个服务；Notion API 每次调用仍要凭证（integration token 或 OAuth access token）。两条路径互不相通：

* hosted connector：凭据由 Hermes 托管，不需要 `NOTION_API_KEY`，在桌面端 / Nous Portal 完成授权。
* skill + curl 直连：必须有 `NOTION_API_KEY`，且目标页面要在 Notion 里 Share 给该 integration，否则 404。

**坑二：cron 的 skill 就绪度检查会误伤。** `notion` skill 的 frontmatter 声明 `env_vars: [NOTION_API_KEY]`，cron 触发前做就绪度检查，缺变量直接 `blocked_config` 拒跑——即便实际走的是 MCP，根本不需要那个 key。修法：摘掉挂载的 skill，prompt 里直接指明走 MCP 工具。

**坑三：cron 的模型解析优先级。** `job.model`（每任务钉住）> `cron.model`（集群默认）> 主 agent 模型（`model.default`，再退到 `HERMES_MODEL`）> 试用模型。所以任务报 429 时，先看是不是被钉到了配额耗尽的模型。
