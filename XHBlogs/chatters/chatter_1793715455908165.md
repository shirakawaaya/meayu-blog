# 情境化文本块：给每一块补一句它自己的上下文

今天读到 Anthropic 在 2024 年 9 月介绍的一个做法，叫 **Contextual Retrieval**，中文一般译作「情境化检索」或「情境化文本块」。核心思路只有一句话：把每个文本块送进嵌入模型和索引之前，先用 LLM 给它写一段很短的情境说明，附在块首。

## 块为什么会"失去上下文"

我们现在的库里存了 3065 个切片，中位数只有 100 字。切法是按「条」来切。

比如这一片：

> 转专业具体程序如下：
>
> 1. 学院制定转专业实施细则及考核办法……

单独看，它不会告诉自己是出自哪份文件、第几条、管学生还是管老师。人在原文里读不会误解，因为上下文都在；一旦切成独立块，这些信息就全丢了。

检索时影响不大——用户问「转专业流程」，向量相似度仍然能匹配上。但到了生成阶段，模型看到的就是一堆没有上下文锚点的片段，只能保守地少说几句。

这在 RAG 领域是一个经典问题，叫「碎片化丧失全局语义」。嵌入模型对孤立片段的编码，和阅读完整文档后的理解，在语义空间里会有明显偏移。Contextual Retrieval 的思路本质上是：用 LLM 补回丢失的全局信息，让每个块的嵌入向量更接近它在原文中的真实位置。

## Contextual Retrieval 怎么做

做法很朴素，四步：

1. **切块。** 按业务规则切成独立片段。
2. **写情境说明。** 对每个块，把整份文档一起喂给 LLM，让它输出一段 50~100 token 的说明：这段属于哪份文件、在讲什么、面向谁。
3. **前置拼接。** 把情境说明拼在块首，得到「情境化块」。
4. **双通道索引。** 用情境化块同时建向量索引和 BM25 索引。

第 4 步是关键——两个通道都要用带前缀的文本，只改一半等于没改。

### 一个具体例子

假设原文档是《XX大学转专业管理办法》，切出的块是：

> 第三条 学生申请转专业，需在第二学期结束前提交申请。

LLM 会输出一段类似这样的说明：

> 本段出自《XX大学转专业管理办法》第三章「申请条件」，面向 undergraduate students（本科生），规定转专业申请的时间节点。

拼接后进入索引的文本变成：

> 本段出自《XX大学转专业管理办法》第三章「申请条件」，面向本科生，规定转专业申请的时间节点。学生申请转专业，需在第二学期结束前提交申请。

## 效果数据

Anthropic 给出的实测指标是 top-20 块的**检索失败率**：

| 配置 | 失败率 | 相对下降 |
| --- | --- | --- |
| 裸块 | 5.7% | — |
| 情境化嵌入 | 3.7% | 35% |
| 加情境化 BM25 | 2.9% | 49% |
| 再加重排 | 1.9% | 67% |

数据来源：[anthropic.com/research/contextual-retrieval](https://www.anthropic.com/research/contextual-retrieval)

成本方面，配合 **prompt caching**（把整份文档作为固定前缀缓存住，每个块只变动后缀部分），生成前缀大约 1.02 美元/百万文档 token。 prompt caching 的机制是：Anthropic Claude API 会对连续相同的请求前缀进行缓存，后续请求若前缀相同则不再重复计算，只收费后缀部分。这对"同一份文档生成多个块的情境说明"场景非常友好。

## 我们其实已经做了一半

入库时我们会生成三份文本：

* `content`：原文
* `embedding_text`：带标题与条号
* `content_tokens`：分词结果

`embedding_text` 本质上就是在做「静态情境」——把标题和条号拼进被索引的文本里。

它和 Contextual Retrieval 的区别在于：静态拼接只是搬运字段，情境说明是让模型读完整份文档后写一句话，能写清「这一条在整章里处在什么位置、为什么存在」。前者是机械拼接，后者是语义补全。

代价也很清楚：

* 3065 个块就是 3065 次 LLM 调用。按文档级 prompt caching 能摊薄，但接入前要把这笔成本算清楚。
* 前缀一旦进入索引，向量索引和 `tsvector` 都得全量重建。
* 文件更新要重算。这是一次性构建成本，不是运行成本。

## 如果要落地，分四步

1. **备好文档级元信息。** 标题、发文号、章、受众、施行日期。
2. **每个块调一次 LLM，输出一句情境说明。** 提示词模板可以复用同一份文档的前缀实现缓存。
3. **情境句前置，写入** `embedding_text` **与** `content_tokens`**。**
4. **重建向量索引与** `tsvector`**。** 检索和生成逻辑都不用改。

有个容易混淆的点：它和我们已有的「上下文回填」不是一回事。回填只在生成阶段把命中片前后各一片拼进去，索引里仍然是单片；情境前缀改的是索引本身，所有下游消费自动受益。 上下文回填（context backfill）是一种粗粒度的检索增强，通过窗口扩展弥补切块造成的语义断裂，但它不改变单个块的嵌入表示；Contextual Retrieval 则是在索引阶段直接修改块的文本内容，属于更根本的预处理手段。两者可以叠加使用。

## 今天还改了两件事

### 记忆：从固定轮次换成滑动窗口加摘要

原来只加载固定 3 轮对话，轮次一多前面的信息就整段丢掉。而且这些历史只喂给「问题改写」模块，生成阶段一个字都不带——用户说过一遍「我大二」，下一轮还得重说。

现在拆成两段记忆：

* **会话摘要**：超出窗口的旧对话压成一段总结。
* **最近 6 轮原话**：保留完整上下文。

两段都进入生成阶段。摘要是异步跑的，只在真有消息滑出窗口时才折叠一次，实测把 14 条消息的会话压成了 86 字。

还有个细节：拒答消息不进记忆。它们没有制度信息，留在上下文里会让模型形成错误先验，以为「这类问题就该这么拒答」。

### 拒答：从一刀切改成三档

原来的拒答只有两种状态：找到和没找到。条款只答了一半，整段也拒答。

现在分三档：

* **条款够答**：正常回答。
* **只够答一半**：先答有的部分，再点明哪一块制度没写。比如辅修学费，制度只写「按省物价部门核定的标准按学分收取」，那就答这个，再补一句没有具体金额，而不是回一句「未找到」。
* **基本无关**：才拒答，但后面加一句「我检索到的最接近的条款是《…》第X条」，让用户知道系统查过了，不是没工作。

判定逻辑也放宽了——从整句相等改成包含关键句。模型经常在那句话前后加半句解释，整句相等会漏判，漏判的拒答又被当成正常回答落库，拒答率统计就失真了。 这个问题在 RAG 评测中很常见，叫「精确匹配偏差」。更好的做法是用 embedding 相似度阈值或者 LLM-as-a-judge 来判断语义层面的匹配，而不是字符串级别的精确匹配。
