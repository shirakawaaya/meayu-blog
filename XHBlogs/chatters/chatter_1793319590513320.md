# **RAG 的四代演进：从流水线到工具箱**

> 起因：被同学问"只做个 RAG？RAG 已死吧"。当时听着不舒服，后来想清楚了一件事——他说的是 naive 那一层，我做的不在那层。与其争论，不如把这几年的演进梳理一遍，顺便确认自己站在哪。

## **一、"RAG 已死"死的是哪一层**

准确的说法是：**死掉的是"通用检索即插即用"的幻想，不是 RAG 这件事。**

naive RAG 的三步流水线——固定大小切分 → 单次检索 → 塞进 prompt 生成——只提供了"最低成本的外部知识接入"。它的价值在 2023 年是真实的（把知识从参数里搬出来），但有两个硬伤：**检索精度不可控**（切分边界由字数决定，与语义结构无关）、**鲁棒性差**（同义改写、错别字、噪声文档、跨文档多跳，任意一项就能让召回崩掉）。

所以"已死"的准确含义是：**这一层已经没有差异化空间了**。LangChain 二十行就能跑，任何 SaaS 都能提供。不是这件事没有价值，是这一层的价值被商品化了。

反方最强的论点不是"RAG 没用"，而是**长上下文**：如果模型能一次读 200K token，为什么还要检索？这个论点在"语料能塞进窗口"的场景下确实成立。但 RAG 有四条它拿不走的护城河：

**护城河长上下文为什么替代不了**私有语料数据不能上传给外部模型实时性制度今天更新，模型权重不会跟着变可溯源回答必须能指到"第几条第几款"，长上下文做不到引用定位成本每次问都塞 200K token，比检索 5 条片段贵两个数量级

行业在 2025 年底基本收回了"已死"的判断——RAGFlow 的年度回顾原话是"远没有像某些大胆预测那样走向消亡"。**死的是 naive 层，活下来的是"检索作为系统能力"这件事。**

## **二、四代演进**

### **第一代：Naive RAG —— 三步流水线**

代码块

```
切分 → 检索 → 生成
```

把外部文本切块、向量化、按相似度取 topK、塞进 prompt。

* **解决了**：知识可以更新、可以溯源到文本。
* **留下的**：切分不看结构、只查一次、只用一个通道、不判断证据够不够。

### **第二代：Advanced RAG —— 在已知会失败的环节上打补丁**

不改流水线的本质，而是在几个失败点上各加一道处理：

**优化做法补的是什么**查询改写检索前改写问题：补全指代、去口语化、扩同义词用户问法与文档写法不一致**HyDE**先让模型生成一个"假想答案"，再用这个假想答案去检索**以"答案相似"替代"问题相似"**——问题与答案的向量分布本来就不在同一空间混合检索向量 + BM25 关键词，按分数或名次融合向量对专有名词、条号、数字不敏感Rerank先粗排召回一批，再用交叉编码器精排双塔召回为了速度牺牲了精度

代价是：**三步变成了六七步**。每加一步就多一个失败点、一份延迟、一组要调的参数。这也是我自己项目里踩到的——加了 Rerank 之后 MRR 变好，但 Recall@5 掉了 3.7 个点。**"加了机器"不等于"变好了"**，每一步都得单独测。

> HyDE 出自 Gao et al., *Precise Zero-Shot Dense Retrieval without Relevance Labels*（arXiv:2212.10496, 2022）。注意它和"四代划分"那篇综述（Gao et al., arXiv:2312.10997）是同一一作的两篇不同论文，引用时别混。

### **第三代：Modular RAG —— 从流水线到可组合模块**

把检索、融合、生成拆成可替换、可组合的模块，试图让不同问题走不同的策略组合。

这一步的野心是"按问题选路"，但工程落地时撞上一个**循环依赖**：

> 要决定走哪条路，先要判断问题的性质；而"判断问题性质"本身就需要知识——那恰好是 RAG 想提供的东西。

我的看法是：这个循环不是死结，但打断它要付代价。主流做法是**训练一个轻量分类器**先判问题复杂度（Adaptive-RAG 就是这么做的：用小模型判断该走单跳、多跳还是根本不需要检索），把"知识"前置到离线阶段。代价有两个：分类器需要标注数据；**判断错了会沿流水线一路放大**——本该多跳的题被判成单跳，后面所有步骤都白做。

这也是我后来想通的一点：**与其让分类器在检索前猜，不如让模型在拿到第一轮结果之后再决定要不要继续**——那就是第四代。

### **第四代：Agentic RAG —— 检索降级为工具箱里的一个动作**

检索不再是"生成前必须执行的步骤"，而是 agent 工具箱里的一个可选动作：

代码块

```
agent 自主决定：要不要检索 → 检索什么 → 第一轮够不够 → 要不要补查 / 换工具
```

三个关键变化：

1. **时机变了**：从"前置固定步骤"变成"按需调用的工具"；
2. **次数变了**：从"查一次"变成"可多轮"，且由模型判断何时收敛；
3. **工具变了**：检索只是工具之一，旁边还可以有结构化查询（查库、查 API）、计算、MCP 等。

学术上已有正式综述（arXiv:2501.09136），给出 single-agent / multi-agent / hierarchical / corrective / adaptive / graph-based 的 taxonomy。所以 agentic RAG 不是营销词，是有坐标的概念。

但有个**顺序问题必须说清**：agentic 站在 advanced 层之上，不是替代它。agent 每一轮判断"证据够不够"，靠的是检索结果的质量；检索本身不稳的时候，agent 只会多查几轮、把噪声叠加。**给漏水的桶换更快的龙头，只会漏得更快。**

而 agentic 最难的不是让它跑起来，是**证明它比固定流水线好**。多轮工具调用引入的失败模式（选错工具、参数编错、循环调用）很难归因。所以我给自己定了条规矩：每个 agentic 特征都必须能设计出"去掉它"的对照组，测不出差异就不进主线。

## **三、几个架构变体**

**变体核心做法解决什么GraphRAG**用知识图谱替代或补充纯向量索引，**显式建模实体之间的结构化关系**（因果、层级、引用、共现）纯向量只能做"局部相似"，答不了全局性问题（如"这批文件的主要争议点是什么"）；图谱 + 社区摘要能做全局归纳**Multimodal RAG**检索范围从纯文本扩展到表格、图像、音频、视频，做跨模态 **grounding**真实文档里关键信息常在图表里（我的语料里就有大量扫描件与表格附件）~~Hybrid RAG~~多路检索 + 融合 + 重排**这个不算独立变体**——它就是 advanced 层的"混合检索 + rerank"，是技术点不是代际

> GraphRAG 的代表工作：Edge et al., *From Local to Global: A Graph RAG Approach to Query-Focused Summarization*（arXiv:2404.16130, 2024）。

关于 hybrid 那条我特意划掉：**四代是时间轴，变体是正交的横切面**——GraphRAG 和 Multimodal 可以出现在任何一代里。把两者混在一起，写论文的相关工作时会显得分类不清。

## **四、回到"鲁棒性"**

我一开始只会说"检索精度和鲁棒性都很有限"，后来发现这词太虚，得拆开才可测。RAG 语境下，鲁棒性至少是五个具体维度：

**维度干扰是什么怎么测系统里怎么应对查询鲁棒**口语、错别字、指代（"那大三呢"）、同义改写同一问题用 5 种问法，看召回是否稳定查询改写 + 意图识别**语料鲁棒**硬换行、标题粘连、页眉页脚、扫描件真实语料跑切片测试，断言无空片、无超长片四条清洗规则 + 三级切片降级链**证据鲁棒**证据不足、证据矛盾（新旧版本并存）无答案题、时效冲突题四道拒答闸门 + 时效版本感知**对抗鲁棒**prompt 注入（"忽略上面的规则"）、越权请求对抗题，合格线是 0 而不是"比较低"权限在 SQL 层，不在 Prompt 层**输出鲁棒**模型编造引用、答非所问引用编号能否解析回证据引用硬校验，未通过则拒答

一句话：**鲁棒性 = 不容易被搞坏、不容易被带偏、出了意外还能撑住**——但在工程上它必须落到"哪个维度、用什么题、看什么指标"，否则只是一句正确的废话。

这也正是"RAG 很简单"这个判断错在哪：**简单的从来不是 RAG，是 naive 那三步。** 真正难的是上面这张表——每一行都要单独设计、单独测，而且彼此牵制（拒答率高说明保守，漏答多说明不可靠，两头都要压）。

## **五、一句话收尾**

同学说的"打通 agent 全链路"，我后来想明白他为什么答不上来：**它不是一个有边界的术语，是一个方向描述**。方向可以很大，但毕设必须有边界——我的边界是"在已经跑通的 advanced RAG 之上，加三个可评测的 agentic 特征"，而不是"做一个 agent"。

至于"RAG 已死"，让它说去吧。**死的是流水线，不是检索这件事；而证明它没死的办法不是争论，是拿出消融数据。**
